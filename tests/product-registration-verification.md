# 상품 통합 등록 구현·검증

## 기준 계약

Backend [PR #374](https://github.com/2026-2-rising-sun/Backend/pull/374)는 2026-11-19 병합됐으며 #372는 종료됐다. 병합 커밋 `3537340c4686fec3b962da8ed02d368829d639af`의 `contracts/api/commercecore-service.yaml`을 기준으로 구현했다.

- 프론트 요청: `POST /api/commercecore/v1/seller/products/registrations`.
- multipart: `file` 이미지, `request` application/json Blob. 인증과 `X-Idempotency-Key`는 공통 HTTP 클라이언트를 사용한다.
- 요청: 상품명·설명·1~100개 SKU의 `optionLabel`, `price`, `initialStock`. category는 선택 필드이며 #61 범위에서 조율한다.
- 다중 옵션명은 공백 제거 후 고유하고 비어 있지 않아야 한다. 재고는 int32 0~2147483647, 가격은 프론트에서 정확히 표현할 수 있는 양의 안전한 정수까지만 입력한다.
- 응답: 상품·이미지 ID, 이미지 URL, 판매 허용 상태와 요청 순서의 모든 SKU별 ID·가격·가용/예약 재고·판매/품절 상태를 보존한다. 임의 대표 가격이나 합산 재고를 만들지 않는다.

## 화면과 생성 성공

신규 경로 `/seller/products/new`는 `SellerProductCreatePage`를 사용한다. 기본정보·이미지·SKU를 함께 검증한 뒤 생성 POST를 한 번 보낸다. 기존 이미지 업로드→JSON 생성→판매 설정→판매 시작 호출은 신규 경로에서 사용하지 않는다.

생성 결과를 직접 표시하며 생성 함수는 상세·주문서·Catalog GET을 수행하지 않는다. 따라서 생성 성공 뒤 조회 지연으로 새 키를 발급하지 않는다. 재고 0은 품절로 표시하며 재고가 있어도 고객 구매 가능을 단정하지 않는다.

기존 수정 화면은 별도로 유지한다. 기본정보·이미지 교체, 가격 변경, 재고 증감, 판매 시작·중지·재개 API는 기존 계약을 사용한다. DRAFT·READY 상품을 자동 판매 시작시키지 않는다.

## 재시도·복구 범위

- 동기 ref 잠금으로 동일 이벤트 루프의 중복 제출을 막는다.
- 전송할 정규화 JSON, 파일명·형식·실제 바이트를 해시해 요청 지문을 만든다.
- POST 전에 인증된 판매자별 sessionStorage에 키·지문·정규화 입력·파일명을 보관한다. 파일 바이트는 저장하지 않는다.
- 네트워크 오류·5xx·잘못된 성공 응답에는 같은 내용·키로 재시도한다. 결과 미확인 중 입력 변경은 새 키를 발급하지 않는다. 409에서도 키를 유지한다.
- 서버 입력 거절은 수정할 수 있도록 기록을 해제한다. 완료 응답은 키와 함께 저장하며, 사용자가 명시적으로 다른 상품 등록을 선택할 때 해제한다.
- 같은 탭에서 화면 재진입·새로고침을 지원한다. 미완료 요청은 입력을 복구한 뒤 같은 이미지 파일을 다시 선택해야 한다. 탭 종료·저장소 삭제 후 복구, 여러 탭 간 요청 공유는 지원하지 않는다.
- 저장소 읽기·쓰기 실패 또는 손상된 기록은 새 키로 덮어쓰지 않는다. 생성 응답을 받은 뒤 결과 보관이 실패해도 화면의 성공 상태를 유지하고 상품 ID 기록을 안내한다.
- 서버는 동시 요청을 직렬화하고 같은 요청에 최초 201 결과를 반환한다. 별도 202 처리 중 응답이나 자동 만료 계약은 없으므로 프론트에서 임의로 추가하지 않았다.

## 백엔드 조회 제약

현재 `SkuSalesService.findSingleByProductIds`는 다중 SKU를 409로 거절하며 기존 판매자 목록·상세도 이 경로를 사용한다. 다중 SKU가 포함된 판매자 목록 전체가 실패할 수 있다. Catalog의 단일 판매 조회도 다중 SKU를 503으로 거절한다.

등록 전후에 이 제약을 안내한다. 다중 SKU 결과에서 기존 상세 경로로 안내하지 않으며 세션에 보관된 최초 결과를 표시한다. 이 기록은 이후 가격·재고 변경을 반영하는 최신 조회가 아니다. 판매자 다중 SKU 목록·상세 조회와 고객 옵션 선택·대표 가격 정책은 추가 백엔드·프론트 연계가 필요하다. 기존 상품 응답을 임의 첫 SKU로 보강하거나 백엔드 계약을 변경하지 않았다.

- 기존 `tests/e2e/features/seller-ui.spec.ts`: 5개 통과. 목록 필터·검색·늦은 응답·DRAFT 화면 회귀 등을 확인했다. 최종 실행은 위 두 파일을 함께 지정해 13개 모두 통과했다.

- `npm run build`, `npm run lint`, `git diff --check` 통과. 기존 hls 번들의 500KB 경고는 남아 있다.

브라우저 검사는 API fixture를 사용한다. 최초 실행은 fixture URL 패턴이 Vite 소스 모듈까지 가로채 로그인 화면을 읽지 못해 중단됐고, 패턴을 서비스 API로 제한한 뒤 재검증했다. 기존 수정 회귀에서도 가격 저장 전부터 일치하는 입력값만 기다려 다음 편집이 재조회로 초기화되는 실패가 있었다. 서버 현재 가격의 화면 반영까지 기다리도록 수정한 뒤 최종 13개를 재실행했다. 단위 검사에서도 이전 분리 생성 계약을 기대하던 테스트를 새 계약에 맞춰 갱신했다.

초기 프론트 검증은 대역 범위였으며 실제 연계는 아래 후속 실행에서 별도로 확인했다. Backend PR의 검사 결과를 이번 프론트 실연동 증거로 대신하지 않았다. S3와 운영 배포는 검증하지 않았다.

## 병합 전 자체 리뷰 보완

등록 경로의 호출 수, 생성 성공/조회 분리, 응답 유실·5xx·409에서의 키 유지, 판매자별 기록 격리, 기존 수정의 version·판매 상태 처리를 점검했다. 복원한 성공 화면에서 다른 상품을 등록하면 이전 상품의 파일명이 재시도 안내에 남을 수 있는 결함을 발견해 현재 요청의 파일명을 상태로 관리하도록 수정했다. 완료 복원→다른 상품→다른 파일명→응답 유실 회귀를 추가한 최종 대역 브라우저 검사 13건이 통과했다. 독립 리뷰나 타인의 승인을 받은 것으로 보고하지 않는다.

## 2026-11-19 실제 통합 API 연계 검증

- Backend `3537340c4686fec3b962da8ed02d368829d639af`, Frontend `9a8b3ebefb65b8ea5501bb83f530e17ddf4f85da`에서 실행했다. 이후 기록 커밋은 운영 소스를 변경하지 않는다.
